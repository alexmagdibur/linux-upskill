# ADR 0001 — образы песочниц: логическое имя + `images.lock.json`

**Статус:** принято.

ТЗ предлагает в манифесте `image: "…@sha256:<registry digest>"`. Локальный образ, собранный `docker build`, не имеет
registry digest до публикации. Решение: манифест содержит логическое имя (`ubuntu-basic`), а
`content/images.lock.json` (генерируется `make images`, не коммитится) сопоставляет его с **content-addressed ID образа**
(`sha256:…`). Worker создаёт контейнер строго по этому ID и отказывает, если образ отсутствует или ID не совпал.
`lab_versions.image_digest` хранит ID на момент публикации версии. Placeholder `REPLACE_WITH_REAL_DIGEST` отклоняется
валидатором манифеста. Базовый образ в `Dockerfile` закреплён по registry digest.

# ADR 0002 — проверка в два шага (exercise → validator)

Часть заданий требует *запустить* артефакт ученика (скрипт, приложение). Исполнять чужой код в контексте проверяющего
скрипта небезопасно (он мог бы подделать вывод проверки). Поэтому `exercise.sh` (доверенный, из контента) запускает
артефакт **от имени student**, вывод игнорируется, а `validate.sh` затем только *читает состояние* под пользователем
`validator` (группа `devs`, не student).

# ADR 0003 — worker не ходит в БД

Worker не имеет учётных данных PostgreSQL: результаты передаются через внутренний HTTP API (`/internal/v1`, токен).
Вся бизнес-логика (скоринг, XP, переходы состояний) остаётся в одном месте, а компрометация worker'а не даёт доступа к БД.

# ADR 0004 — XP

`UNIQUE (user_id, session_id, reason)` по ТЗ + дополнительный `UNIQUE (user_id, reason)`: причина вида
`lab_first_completion:<slug>` выдаётся один раз на пользователя даже при конкурентных проверках в разных сессиях.
Прогресс блокируется `SELECT … FOR UPDATE` внутри транзакции финализации.
